Beschrijving

In de verschillende OpenAPI specificaties worden datum-tijd velden aangeduid met het type “string” en als formaat “date-time“.
Bij de OpenAPI standaard van dit formaat (https://spec.openapis.org/registry/format/date-time ) staat het volgende:

  • The date-time format represents a date and time as defined by date-time - RFC3339.

In de verwijzing naar RFC3339 staat volledig beschreven hoe de datum tijd notatie mag en moet zijn.

Nu is het verwarrend dat in de EduV specificaties de volgende opmerking staat:

        dateCreated:
          type: string
          description: 'Indicates the date and time the object was first created. Format: Conform openapi in ZULU time zoals gespecificeerd in RFC 3339, section 5.6.'
          format: date-time
          example: "2017-07-21T17:32:28Z"

Dus conform OpenAPI én RFC3339 én in ZULU time?

Nu wordt zowel in de OpenAPI standaard en RFC3339 niets afgedwongen met betrekking tot ZULU time maar juist verschillende tijdzones ondersteunt.
Dus is dit bedoeld als een voorbeeld van een bepaalde datum-tijd, of mag het alleen maar ZULU tijdzone zijn?

Nu is dat laatste onlogisch en onwenselijk om meerdere redenen:

  • Als het goed is (is ook het advies van SEM) wordt er gebruik gemaakt van OpenAPI importers en zoveel mogelijk standaard packages en libraries voor bijvoorbeeld JSON

  • Alle OpenAPI en JSON libraries ondersteunen de volledige RFC3339 datum-tijd (dus ook tijdzones en msec nauwkeurigheid)

  • Er staat nergens een beperking qua controle dat het perse ZULU tijd moet zijn (dit staat alleen als opmerking) dus een JSON schema validator controleert hier niet op

  • Het is foutgevoelig om iedereen te verplichten om overal in de code de lokale tijd (wij hebben tijdzone Amsterdam, 1 of 2 uur offset afhankelijk van zomer en wintertijd) te moeten omzetten naar UTC c.q. ZULU tijd. Default ondersteunt alle software het dus waarom zou je het beperken?

  • Voor debuggen is het onhandig om niet de lokale tijd te kunnen zien maar zelf 1 of 2 uur moeten optellen

  • Ondersteuning voor landen en gemeenten in het Caribisch gebied is problematisch, omdat deze helemaal een andere tijdzone hebben, dus is ondersteuning voor tijdzones cruciaal

Tot nu toe ondersteunen alle partijen de volledige JSON c.q. RFC3339 tijdnotatie, maar zorgt het bij het testen en koppelen en valideren wel voor verwarring.

Beschrijving

Biedt de volgende alternatieve Consent API aan. Desnoods als onderdeel van de huidige, maar dan zodanig dat de huidige niet geïmplementeerd hoeft te worden door partijen. N.b. deze variant is gebaseerd op de SEM PoC en lijkt sterk op de eigen consent API die Magister nu beschikbaar heeft in productie, waardoor de overstap voor partijen die deze API reeds gebruiken minimaal zal zijn.

De nieuwe API bestaat uit één enkel endpoint dat aangeroepen wordt zonder parameters. Het levert alle consent op die gegeven is per API-client.

Get UnitConsents

De body van deze call bestaat uit een JSON document met daarin geneste arrays:

  • top level: ‘client’, vooral om uitbreidbaar te blijven

    • Met deeplink naar de consent UI. Die kan daardoor getoond worden vanuit het product van de client.

    • Met mogelijkheid voor aanvullende consent per gebruiker en ook de mogelijkheid om die via deeplink in te laten voeren van het product van de client.

    • daarin: 'tenants' (array) > Dit kan voor iedere partij anders ingericht zijn. Het kan overeenkomen met een onderwijsaanbieder, maar dat hoeft niet.

      • met per tenant: 'units' (array) > Dit kan ook voor iedere partij anders zijn. Als het systeem puur op Edu-v gebouwd is dan is het wellicht 1 unit voor een onderwijsaanbieder. Het is echter altijd de structuur in het bronsysteem, maar dan als platte lijst. In het bronsysteem is dit het niveau van consent geven.

        • op unit niveau wordt de link gelegd naar op dit niveau beschikbare Edu-v identifiers. Het is uitsluitend de bedoeling om hiermee een ingang te bieden en niet om een kopie van het organisation endpoint te bieden. De afnemer kan altijd met het ontvangen id de andere relevante identifiers opvragen bij het administratiesysteem. De requirement moet zijn dat er minimaal 1 Edu-v compatibele identifier beschikbaar moet zijn.

  • er wordt geen overbodige informatie uitgewisseld en ook geen informatie die al in andere Edu-v endpoints beschikbaar is.

Hieronder een concrete uitwerking van een response. De id’s op ieder hoofdniveau zijn de eigen identifiers van het bronsysteem en spelen geen rol in Edu-v. Onderbouwing van nut of noodzaak

samenvatting onderbouwing:
De consent API geeft geen inzicht in de onderdelen van de school waar werkelijk consent op geboden is. De consent API is onnodig complex met als gevolg lage adoptie. De inhoud is op onderdelen misleidend. De aanname dat scopes per school per client bepaald kunnen worden is niet correct, wat leidt tot een verwarrende API die niet kan werken in de praktijk. De handshaking is overengineered voor de doelen die het tracht te bereiken. Het gevolg van een te kostbare API is nu geen API. Scholen worden beter bediend met een eenvoudige en daardoor laag-drempelige koppeling die wel door alle partijen geïmplementeerd wordt.

Toelichting:

  1. De huidige consent API is te complex en in veel gevallen onbruikbaar. Dit verklaart de lage adoptie.

  2. Een eenvoudigere consent API was waarschijnlijk wel succesvol geweest, maar de huidige opzet vraagt teveel van alle partijen.

  3. Leveranciers (zoals Magister) wijken hierdoor uit naar bestaande eigen Consent oplossingen en bieden die kosteloos aan. Die consent API alternatieven vinden nu wel adoptie onder afnemers, wat bevestigd dat een eenvoudigere consent API wel succesvol kan zijn en van grote meerwaarde is.

  4. Het consent request bevat API scopes per school. Inherent aan de OAuth2 implementatie waarbij een token aangevraagd wordt zonder schoolcontext is echter dat het token en de daarin toegestane scopes gelden voor de hele client en dus voor alle scholen.
    concreet proces: client vraag token aan (zonder schoolcontext) met gewenste API scopes. De AS keurt deze goed als de scopes toegestaan zijn op client niveau: dus voor alle scholen. De resource server ontvangt een aanvraag van de client met een token waarin de scopes staan waar de client toegang toe heeft. Pas bij aanvraag naar de resource server is de school bekend en dan heeft de client dus al een token met toegang tot de scopes. Oftwel wat Edu-v tracht te doen is onmogelijk met Api scopes.
    Merk op dat dit exact overeenkomt met de pagina M2M identificatie, authenticatie en autorisatie. https://edu-v.atlassian.net/wiki/spaces/AFSPRAKENS/pages/10846209/M2M+identificatie+authenticatie+en+autorisatie#Proces%3A-interactieanalyse--identificatie-en-authenticatie-middels-OAuth-2.0
    Het diagram op die pagina toont duidelijk de scheiding tussen de interactie met de autorisatieserver wat op leverancierniveau plaats vindt en vervolgens onder de dikke zwarte lijn de interactie met de resourceserver die wel bewust is van de schoolcontext. De toelichting onder het diagram stelt zelfs letterlijk “De identificatie, authenticatie en de autorisatie op gegevensdiensten (scopes) is na stap 10 afgerond.” Dat is correct! De extra authenticatiestappen bedoeld in stap 13 kunnen dus niet over API scopes gaan, want dat is dan al een gepasseerd station. Dit gaat over de autorisatie in het systeem van de resourceserver die per school autorisaties heeft. De werking van die autorisatie zou bij voorkeur niet moeten zijn dat het token afgekeurd wordt, maar dat de data die geleverd wordt beperkt wordt. Bedenk dat in het diagram het scenario onder de zwarte streep herhaald wordt voor iedere school waarvan de afnemer gegevens nodig heeft: Dus er wordt 1x een token aangevraagd, daar zitten de scopes in, en vervolgens wordt met dat token voor iedere school data opgehaald. Het is dan onlogisch dat je op hetzelfde token vervolgens voor de ene school een error krijgt en voor de andere niet. Het token is gevraagd en gemaakt zonder relatie tot een school en het is daarna geldig voor alle scholen zonder kunstjes te moeten doen. Als de ene school wil autoriseren op minder data dan een andere school dan is dat prima, maar dan dus niet door het token af te keuren. Daar is immers niets mis mee.

  5. API-scopes zijn in principe niet muteerbaar. De reden is dat wanneer een school eenmaal consent gegeven heeft, dat consent niet zomaar uitgebreid mag worden naar nieuwe scopes (die dus gelden voor alle scholen). Dit impliceert dat een wijziging van API scopes nooit over de consent API zal lopen, maar via een apart proces waarbij naar scholen gecommuniceerd moet worden dat de scope verbreed wordt. indien scholen niet reageren zal de consent ingetrokken moeten worden zodat de school opnieuw consent kan geven voor de nieuwe scopes. Oftewel het aanvragen van API scopes via de consent API is zinloos.

  6. API-scopes zijn niet beperkt tot Edu-v scopes. Het staat leveranciers vrij om aanvullende scopes te definiëren en extra gegevensdiensten aan te bieden die niet onder edu-v vallen, daar horen extra scopes bij. Doordat Edu-v scopes als enumeratie definieert waar deze nieuwe scopes niet onder vallen kunnen deze niet uitgewisseld worden. Als er al API scopes gedeeld worden via de consent API dan moet dat dus per definitie een uitbreidbare lijst zijn die niet beperkt is tot scopes die bekend zijn bij Edu-v.

  7. Het ‘api' veld is misleidend en gevaarlijk en moet verwijderd worden. De lijst van API’s speelt geen rol in de consent bepaling. In edu-v heeft iedere API immers eigen API-scopes, die toegang tot de API geven. Als de lijst van API’s niet exact overeenkomt met de API’s waar de API scopes toegang toe geven dan is er sprake van misleidende informatie. Immers als je deze informatie toont aan een beheerder dan lijkt het wellicht als partij ‘x' geen toegang heeft tot de ‘Students API’, maar als de client voor die partij wel de scope ‘eduv.student.basic’ bevat dan heeft die partij wel degelijk toegang tot de ‘Students API’ ook al toont het 'api’ lijstje deze niet. Het is dus erg onverstandig om een dergelijk afgeleid veld mee te nemen in de API want het kan eigenlijk alleen maar fout gaan. Dat risico bestaat niet als alleen de lijst van scopes uitgewisseld wordt. Echter die lijst wordt al gedeeld in de tokenaanvraag (standaard OAuth) en is daar niet beperkt tot Edu-v. Aangezien de OAuth implementatie verplicht onderdeel van Edu-v is, is de lijst met API scopes dus overbodig. Partijen kunnen hier beter beschikbare standaard onderdelen voor gebruiken.

  8. De Sis-api’s zijn gewijzigd waardoor het nu mogelijk is om op basis van identifiers gekoppeld aan één of meer administratieve eenheden data uit te wisselen 'gefilterd' op die administratieve eenheden. Het gevolg hiervan is dat de Consent API niet toont waar de school nou werkelijk toestemming voor gegeven heeft. De school kan van een onderwijsaanbieder 1, 2, 3, .. of x units toestemming geven. In de consent API zoals deze nu is, zie je geen enkel verschil. Toch mis je de helft van de leerlingen en kun je dat niet verklaren. Daarom is er behoefte aan een Consent API zoals Magister die nu biedt en die de consent per unit toont. Op die manier kunnen verschillen (bijvoorbeeld tussen UWLR en Edu-v) eenvoudig verklaard worden.

  9. De Consent API bevat een compleet transactiemodel waarbij aan beide kanten allerlei identifiers geregistreerd moeten worden. Tevens forceert het een technische complexe en daarmee dure notificatiefunctie in het product. De achterliggende behoefte kan ook anders opgelost worden en heeft voor een deel helemaal geen oplossing nodig. Alle leveranciers moeten al een vorm van auditlogging bieden waarin het in-en uitschakelen van consent geregistreerd wordt. In het zeer zeldzame geval dat er onenigheid bestaat over het in-en uitschakelen van consent, kunnen deze tijdsgebaseerde logs eenvoudig geraadpleegd worden en is de overkill van een transactiesysteem in de API is dus overbodig.

  10. Een manko van het huidige consent transactiemodel is dat het niveau waarop consent gevraagd wordt maar in een zeer uitzonderlijk geval exact overeenkomt met de verzameling van schoolonderdelen die de beheerder daadwerkelijk toe zou moeten staan. In feite vraagt dit mechanisme standaard om een ‘hand' waar in werkelijkheid een 'vinger’ gewenst is: lees de leverancier heeft geen toegang nodig tot de complete RIO Onderwijsaanbieder, maar alleen een onderdeel daarvan, maar kan dat niet vragen. Je wil vanuit Edu-v sturen op dataminimalisatie, maar de huidige opzet lokt het geven van te brede toestemming uit.

  11. De motivatie voor een complexe API met handshaking is om het ‘eenvoudiger’ te maken om consent in te regelen aan beide kanten van een verbinding. Dat kan echter ook op een andere manier. De URL naar de consent-UI van de client kan eenvoudig gedeeld worden. Doordat deze basisinformatie altijd zichtbaar is in het response kan bij ontbrekende consent eenvoudigweg de consent UI geopend worden waar de beheerder vervolgens de toestemming kan geven. In het geval dat het twee verschillende beheerders zijn, kunnen ze simpelweg even naar elkaar toe lopen, of desnoods de URL mailen naar de collega. In de meeste gevallen (zelfde beheerder of collega in zelfde gebouw) is deze oplossing sneller en effectiever. Hij is in ieder geval een stuk pragmatischer en veel eenvoudiger om te realiseren.
